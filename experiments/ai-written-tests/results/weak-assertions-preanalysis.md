## Conventions used in this pass

- A **hit** is proposed only when the checklist text clearly applies. Anything arguable is in the **borderline** table of each suite, not counted.
- **W1**: proposed as a hit only when the status (or `ok()`) is the only assertion on the primary response and nothing else is checked. When the primary response is status-only but a GET read-back / state check follows (typical 403/201 tests), it is listed as borderline, applied identically to H, A and B.
- **W3 / cleanup and setup**: setup POSTs and teardown DELETEs inside shared fixtures/helpers/hooks are listed as borderline per affected test (they are not the subject of the test), never as hits.
- **W4**: a body used with no schema and no explicit type check, and not compared in full, is a hit; a body compared by exact `toEqual` to a known object but without a schema is borderline.
- **W6** for failed `POST /auth` or a GET: borderline (no state could change).
- **W7**: `ok() === false` is borderline because the exact status (500/405) comes from the stub probe log, not from the API documentation that W7 requires.
- Nothing outside the checklist was judged. One observation that sits at the edge of W8 is listed as borderline only: in suite B, `z.object()` strips unknown keys (checked with zod 4.6.5 from suite-b), so `expect(body).not.toHaveProperty('token')` after the parse can never fail.
